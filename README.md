# SoloID

The Solo Identity Provider. Just for you.

A small self-hosted OpenID Connect provider: one JSON file, email/password login,
multiple users and apps, and no database. Built with TypeScript, Hono, and
server-rendered HTML styled with Tailwind. No browser JavaScript, signup, second
factor, or refresh tokens.

**Deploy one container with Docker Compose behind your existing HTTPS reverse
proxy.** SoloID does not deploy or manage that proxy.

## Start with Docker Compose

Requires Docker with Compose. Run the commands below from `deploy/` in a checkout
of this repository. Until an image release is published, build it locally:

```sh
docker compose build
mkdir -p config
chmod 700 config
umask 077
docker compose run --rm soloid dist/cli.js init > config/config.json
docker compose run --rm soloid dist/cli.js hash
docker compose run --rm soloid dist/cli.js gen-secret
```

`init` creates fresh keys and a **skeleton**, not working default credentials.
Edit `config/config.json`:

1. Set `issuer` to the public HTTPS origin, e.g. `https://id.example.com`, without a
   trailing slash or path.
2. Set your email and name. Paste the output of `hash` into `password_hash`.
   `hash` prompts twice without echo. It requires 12–1024 characters/bytes
   (at least 12 characters, at most 1024 UTF-8 bytes).
3. Configure each app's exact callback URL. Give the app the `client_secret` from
   `gen-secret`; put only its `client_secret_hash` in SoloID's config.
4. Keep each user's `id` unchanged for that person's lifetime. Generate a different
   UUID for every additional user; never reuse a deleted user's ID.

The runtime container uses UID/GID **65532**. On a standard Linux Docker host, make
the config readable by that group, but not world-readable:

```sh
sudo chown -R root:65532 config
sudo chmod 750 config
sudo chmod 640 config/config.json
docker compose run --rm soloid dist/cli.js check --config /config/config.json
docker compose up -d
docker compose logs -f soloid
```

Use `sudoedit config/config.json` for subsequent edits. Rootless Docker and other
hosts may need different ownership/ACLs to let container UID 65532 read the file.
The directory needs execute permission; the file needs only read permission.
Keep the config and backups outside version control. **The private signing key and
cookie secret are secrets even though passwords are hashed.**

The container has a read-only root filesystem, drops Linux capabilities, runs
non-root, and checks `/healthz`. It publishes `127.0.0.1:3000` by default. Change
the host port with `SOLOID_PORT`; keep it unreachable from the public Internet.
No writable volume is required. Mount the config directory, rather than an
individual file, so atomic file replacements are visible on reload.

## Connect your existing reverse proxy

Use a dedicated hostname at `/`, terminate TLS at the proxy, preserve cookies,
and disable caching. Do not add another login/authentication layer in front of
SoloID's protocol endpoints. SoloID uses its configured issuer for URLs and
checks login/logout POST `Origin` against it. Forwarded IP headers do not affect
authentication or rate limiting.

For Caddy running on the same host, add this to **your existing Caddyfile**:

```caddyfile
id.example.com {
    reverse_proxy 127.0.0.1:3000
}
```

If Caddy is in another Compose project, remove SoloID's `ports` mapping and join
the existing proxy network instead:

```yaml
services:
  soloid:
    # Keep the other service settings from deploy/compose.yaml; remove ports.
    networks: [proxy]
networks:
  proxy:
    external: true
    name: your-existing-proxy-network
```

Then use this alternative in the existing Caddyfile:

```caddyfile
id.example.com {
    reverse_proxy soloid:3000
}
```

For a proxy on another host, bind with `SOLOID_BIND` to a private interface and
firewall access to the proxy only. Use a trusted/private network for the HTTP hop.

## Configure users and clients

See [deploy/config.example.json](deploy/config.example.json) for the shape of the
file. Its placeholder keys and hashes intentionally fail validation; use `init`
to generate real keys. Unknown config fields are rejected.

| Field | Meaning |
| --- | --- |
| `issuer` | Public origin. HTTPS required, except `http://localhost[:port]` for development. |
| `secret` | Canonical base64url encoding of 32 random bytes, generated by `init`. |
| `signing_key` | RSA private JWK, at least 2048 bits, generated by `init`. |
| `previous_public_keys` | Old **public** RSA JWKs to retain during signing-key rotation. |
| `session_ttl` | Default `12h`; positive integer followed by `m`, `h`, or `d`, up to 30 days. |
| `users[].id` | Stable opaque subject (`sub`). Unique, 1–128 ASCII letters/digits/`_`/`-`. |
| `users[].email` | Unique after trimming and lowercasing; used for login. |
| `users[].name` | Optional display name returned with the `profile` scope. |
| `users[].email_verified` | Defaults to false. Set true only after independently verifying the address. SoloID sends no verification emails. |
| `users[].password_hash` | Argon2id PHC hash generated by `hash`. Fixed 64 MiB, 3 passes, 4 lanes, 16-byte salt, 32-byte output. |
| `clients[].client_id` | Unique app identifier with the same character limits as user IDs. |
| `clients[].name` | Optional friendly label on the login form. |
| `clients[].client_secret_hash` | Required for confidential clients. Generated by `gen-secret`. |
| `clients[].public` | Set true for clients unable to keep a secret; then omit the secret hash. |
| `clients[].redirect_uris` | Exact HTTPS callback URLs, or HTTP localhost for development. No wildcards, fragments, or URL credentials. |
| `clients[].post_logout_redirect_uris` | Optional exact return URLs after logout. |
| `clients[].allowed_users` | Optional list of **user IDs**, not emails. Omit for all configured users; `[]` denies everyone. |

At least one user and client are required. All apps are owner-approved; there is
no consent UI. Rate limits are deliberately not configurable.

## Configure an app

Discovery: `https://id.example.com/.well-known/openid-configuration`.

- Use **authorization code flow with PKCE S256**, including confidential clients.
- Scopes: `openid`, optionally `email` and `profile`.
- Client authentication: `client_secret_basic`, `client_secret_post`, or `none`
  for public clients.
- ID tokens use RS256, last 5 minutes, and include `auth_time` and the requested
  nonce. Access tokens last 15 minutes and are **only for SoloID's `/userinfo`**,
  not general-purpose credentials for your APIs.
- Refresh tokens are not issued. `offline_access` is ignored and not granted.

Example Grafana settings (adjust URLs and supply its client secret securely):

```ini
[auth.generic_oauth]
enabled = true
name = SoloID
allow_sign_up = true
client_id = grafana
scopes = openid email profile
auth_url = https://id.example.com/authorize
token_url = https://id.example.com/token
api_url = https://id.example.com/userinfo
use_pkce = true
use_refresh_token = false
login_attribute_path = sub
email_attribute_path = email
name_attribute_path = name
```

Set Grafana's `GF_AUTH_GENERIC_OAUTH_CLIENT_SECRET` through your secret-management
mechanism. Register `https://grafana.example.com/login/generic_oauth` in SoloID.
This is a configuration example, not a claim that every Grafana version was tested.

## Operations

Run from `deploy/`:

```sh
# Validate before reloading; failed reloads keep the old configuration.
docker compose run --rm soloid dist/cli.js check --config /config/config.json
docker compose kill -s HUP soloid

# Restart / logs
docker compose restart soloid
docker compose logs -f soloid

# Once images are released, use an explicit version in SOLOID_IMAGE if desired.
docker compose pull
docker compose up -d
```

- A valid reload is atomic, keeps failure counters, and drops pending authorization
  codes. A restart also clears counters. Signed sessions survive when keys and
  user passwords are unchanged; an interrupted sign-in must be started again.
- Removing a user/client or tightening `allowed_users` stops new grants and
  `/userinfo` access. Changing a password hash invalidates that user's SoloID
  sessions and access tokens. Apps may retain their own sessions regardless.
- `/logout` asks for confirmation, then clears SoloID cookies. It supports
  `client_id`, signed `id_token_hint`, `post_logout_redirect_uri`, and `state`.
  There is no front-channel or back-channel app logout, and copied cookies cannot
  be individually revoked.
- For signing-key rotation, replace `signing_key` and retain the previous public
  JWK in `previous_public_keys` for at least 15 minutes. Do not copy the old
  private fields there. Changing `secret` invalidates all SoloID sessions and
  `/userinfo` access, but does not change user IDs.
- Protect access logs at your proxy: callback query strings contain authorization
  codes. SoloID logs outcomes and email addresses as JSON, never passwords, codes,
  tokens, or keys. Emails in logs are personal data; set retention accordingly.

## Security and limitations

This is a small, deliberately limited provider, **not an OpenID-certified product**.
Review it before trusting it with sensitive applications.

- Unknown emails undergo the same Argon2id verification as known users, using a
  dummy random-password hash with identical settings. Failures say **Login Failed**
  (401). Equivalent work reduces timing-based enumeration; it cannot guarantee
  identical wall-clock times. The HTML has the same structure, apart from the
  submitted email and transaction-specific CSRF value.
- Five failed passwords per normalized email in a one-hour window lock that email
  for 15 minutes. Attempts while locked say **Login Failed (Rate Limited)** (429)
  with `Retry-After`; the fifth failure itself is still 401. Successful login
  clears that email's count. Unknown emails behave the same. IPs are never keys.
- Concurrent attempts for an email are serialized. Argon2 verification is capped
  at two concurrent jobs, login queues at 32 requests, and tracked identities and
  authorization codes at 10,000 each. Capacity exhaustion returns 503, not an
  authentication bypass. Per-email lockouts allow denial of service by someone who
  knows an email. Rotating email inputs can still consume CPU; use infrastructure
  resource limits for availability. Expiry alone is not a memory bound.
- Authorization codes are random, stored only in memory, expire after 60 seconds,
  and are consumed atomically once. Restarting or reloading invalidates them.
  Run **one process/replica**, not clustered or serverless.
- Login and logout use a signed transaction cookie, CSRF form token, and exact
  Origin check. Secure, HttpOnly, SameSite=Lax cookies use `__Host-` names in HTTPS
  deployments. Development HTTP localhost cookies omit the Secure flag/prefix.
  Starting another login in the same browser replaces the pending transaction.
- `prompt=none`, `prompt=login`, `prompt=select_account`, and `max_age` are handled.
  Explicit consent requests are rejected (`consent_required`); claims requests,
  request objects, PAR, implicit/hybrid flows, dynamic registration, token
  introspection/revocation, and custom-scheme native callbacks are not supported.
- Server-side apps often maintain their own sessions, so token expiry need not
  interrupt users. Apps requiring a fresh access token must redirect through
  SoloID again; an active SoloID session usually avoids another password prompt.
  SPAs may lose unsaved state during navigation, and native apps may reopen a
  browser. There is no unattended/background token renewal or hidden-iframe flow.
  Clients requiring refresh tokens may be incompatible.

## Development and tests

Node 22.12+ and npm:

```sh
npm ci
npm run typecheck
npm run build
npm test
npm run timing
```

Tests use disposable keys and credentials. They cover the HTTP security contract,
concurrent code replay and login failures, expiry, CLI operations, real-process
SIGHUP reloads, and a complete `openid-client` flow including signature verification
through discovery/JWKS. `timing` compares 100 wrong-password samples for known and
unknown emails; it is a diagnostic rather than a CI pass/fail threshold.

With Docker available, `bash scripts/compose-smoke.sh` builds and boots the Compose
service, checks discovery/JWKS/CSS and the CLI, and removes its disposable config.
It refuses to overwrite `deploy/config/config.json` and uses host port 3000.

For local development, generate a config with `npm run cli -- init`, set its issuer
to `http://localhost:3000`, then run `SOLOID_CONFIG=/absolute/path/config.json npm start`
after building. `npm run dev` watches TypeScript; rebuild CSS when changing styles.
Do not use the test fixture generator for a real deployment.

CI runs tests and the Compose smoke test. A separate workflow publishes an amd64
image to GHCR only when a maintainer pushes a `v*` release tag. A PR does not publish
an image or deploy anything. The implementation decisions are recorded in [PLAN.md](PLAN.md).
